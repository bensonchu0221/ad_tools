## P0

### #1 背景同步

- **查證**：正式服務目前**不是** `--cpu-throttling`。我用 `gcloud run services describe` 查，結果是 `run.googleapis.com/cpu-throttling=false`。`cloudbuild.yaml` 裡改成 `--cpu-throttling` 的那行還在工作區、沒有 commit，所以第 1 點眼下不會發生，但只要那行一部署就會發生。第 2 點（沒有跟 06:00 排程互斥，`sales/store.ts` 的暫存表名稱是固定的）和第 3 點（白天把財務改到一半的試算表寫進去、`rejected` 沒處理）不需要任何前提，現在就成立。
- **處理**：拿掉 `route.ts syncTrigger`，改成鎖定後由隔天 06:00 的 `sales-sync` 排程帶上。畫面上的提示也改成「明天 06:00 同步後 PAC 才看得到」。
- **取捨**：PAC 會晚一天才看到。通常鎖定都在上刊前，晚一天可以接受。之後真的要即時，再做 Cloud Tasks（在請求內執行）＋`GET_LOCK('sales_sync')`，把建議的做法完整做出來。
- #16-4（`setProjectStatus` 沒有觸發同步）和 #16-5（錯誤通知的日期用 UTC），跟這段程式一起移除了。

### #2 作廢不會同步到 BQ

- **處理**：
  - `store.ts lockedSnapshot` 除了勾稽一致的專案，也回報「曾經一致、現在不一致」的專案，標成 `voided`。判斷依據是 `iocue_events` 裡有沒有 `reconciled` 事件。
  - `sales/iosys.ts appendIosys` 收到 voided 時，用同一個 `source_ref` 輸出 IO，所以 id 不變。內容如下：
    - `status`：已作廢。如果只是 Cue 被作廢、IO 還簽著，寫成「暫停（Cue 待重新確認）」。
    - 金額歸 0，`note` 保留原本的未稅金額。
    - allocations、assignments、cue_lines 都輸出空的，`mergeRows` 會把整組換成空的。
  - 因為這張 IO 今天還在，不會被當成 `vanishedIoIds` 誤報。
- **測試**：`verify_iocue`「iosys 作廢」。模擬兩天的合併：id 不變、狀態作廢、三張子表變 0 列、`vanishedIoIds` 是空的。另外 `verify_iocue_flow`「#2＋#10」走一次完整的 DB 流程。

### #3 新版草稿汙染已簽署 IO

- **處理**：
  - `iocue_io_versions` 新增 `project_json` 欄，由 `store.ts MIGRATIONS` 用 `ALTER TABLE ADD COLUMN` 補上。
  - 送審時把合約欄位凍結進這欄，退回草稿時解凍。凍結的欄位是：案件名稱、經銷商、屬性、品牌、付款方、統編、發票抬頭、開票主體、AE、AM、付款條件、折讓。
  - `service.ts projectFor`：版本送出後，PDF、內容雜湊、`lockedSnapshot`（也就是 BQ）一律用凍結的那份。
  - 作廢新版時，把專案列還原成現行版凍結的值，堵住「開 v2 改資料再作廢 v2」的繞過。
- **測試**：`verify_iocue_flow`「#3」。在 v2 草稿把付款方改掉後：v1 的雜湊不變、快照與 PDF 仍是原付款方；作廢 v2 後專案列也還原。

### #4 審核中可以退回 Cue 偷改

- **處理**：
  - `cueAction`：Cue 跟一張「審核中」或「待客戶簽署」的 IO 同批時，`reject` 和 `void` 一律擋，要從 IO 那邊退回或作廢。
  - `ioGate`：approve 和 sign 前都要確認同批 Cue 是「待確認」，而且 `checksBlock` 為 false。

### #5 核准先印 PDF 才驗權限

- **處理**：
  - 交易外先用快照跑一次 `ioGate`（版本、同批 Cue、核對、角色、自審）。沒權限或自己送審的人，連 Chromium 都不會開。
  - 核准時間只取一次（`at`），PDF 上的核發日和 DB 的 `approved_at` 都用它。
  - 交易內重算內容雜湊，跟印出來的 PDF 比對，不一樣就作罷。
  - 交易失敗時刪掉剛上傳的 PDF（新增 `core/gcs.ts deleteIocueFile`）。
  - `uploadEvidence` 也一樣：交易內鎖住專案列、再確認一次狀態，失敗就刪檔。
- **測試**：`verify_iocue_flow` 的三個 #5 項目：
  - 沒權限、自己送審：Chromium 呼叫次數是 0，GCS 沒有多檔。
  - 印 PDF 的過程中改掉一列的說明：核准作罷、PDF 被刪；正常核准時，PDF 核發日等於 `approved_at` 換成台北時間的日期。
  - 上傳的過程中 IO 被作廢：沒寫進 DB，GCS 也沒留檔。

### #6 簽署時誤作廢舊 Cue

- **處理**：
  - **一版 IO 配一版 Cue**：IO 送審時一定要帶一版 Cue 草稿，否則擋下。
  - sign 時一定有同批「待確認」的 Cue，這個由 `ioGate` 保證。舊的已確認 Cue，只在這次真的鎖定了新 Cue 時才作廢，所以不會再出現「由 Cue vundefined 取代」。
  - `newVersion('io')`：
    - 有 Cue 草稿，就把它改掛到新版 IO（新增 `store.ts setCueIoVer`），不多開一版。
    - 有「待確認」的 Cue 新版，要先確認或退回，才能開 IO 新版。
- **測試**：`verify_iocue_flow`「#6」照情境 A 走完整條。結果是 IO 為 `[void, signed]`，Cue 為 `[void（由 Cue v2 取代）, confirmed]`，勾稽一致。
