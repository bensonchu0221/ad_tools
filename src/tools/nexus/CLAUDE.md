## nexus 資料倉庫核心（tool#9）

- **目的**（2026-09-23 使用者定調）：四平台（D/R/M/P）**全部有在跑的帳戶**「素材 × 日」數據每天抓一次存進 BQ，之後 Report Hub、整合週報等內部報表工具都改讀倉庫、不再各自打 API；主管／老闆用 **Looker Studio** 直接看，會議上以 **customer（客戶）** 角度看整體。
- **位置**：BQ `popinpoc1.reporting`（使用者拍板用既有 dataset、不另開），表名一律 **`nexus_` 前綴**（使用者指定，呼應 Cloud SQL 跨工具共用庫 `nexus`）。同 dataset 有主管的 `coupang_report*`（WRITE_TRUNCATE 只作用在那張表，碰不到我們；但 dataset 擁有者是主管，建表前使用者已自行知會）。
- **表**（定義在 `schema.ts`，單一真相）：
  - `nexus_d_ad_daily`／`nexus_r_cr_daily`／`nexus_m_teaser_daily`／`nexus_p_creative_daily`：各平台原生欄位全收（D 含 cv/mcv/mcv2＋cv_* 11 種；R 含 behavior0-6＋`exposure_report` 可視曝光＋agent 代理商；M 三階漏斗＋幣別；P 含 view_25~100、viewable）。**只存可加總的計數／金額，比率一律不存**。id 全轉 STRING。標題／落地頁／縮圖直接冗餘在事實表（量小，省 Looker join）。
  - `nexus_device_daily`：四平台共用；D/R/P 到 campaign、M 只到帳戶（campaign_id NULL）；**D 的 Others＝平台總數 − PC − Mobile**（平板等平台不給 base 指標；2026-09-24 以前只收 PC/Mobile，平板流量整塊不見，帳戶 24961 少 9.6%，已改並回補）；轉換事件放 `events`（JSON 字串，平台原生事件名→次數），讓報表工具依自己的 cv 桶取用。
  - `nexus_customer_account_map`：**先建空表當介面**。customer 四平台 API 都沒有（見 memory ad-data-warehouse-plan），目前 AE/AM 在系統外維護；之後不論改 Sheet 外部表或 Cloud SQL＋web UI 同步，只要表名欄位不變，view 與 Looker 不用改。
  - view `nexus_integrated_daily`：四平台 UNION 成同一套欄位＋LEFT JOIN customer（對照表先收斂成一帳一列，防誤填重複放大數字；沒對照到的 customer 退回 account_name）。**不含轉換**（四平台語意不同，硬加總會誤導）。
  - 全部事實表**日分區＋requirePartitionFilter**：不帶 date 條件的查詢會被 BQ 拒絕（防全表掃描）。Looker 要設日期範圍。
- **排除清單＋拿不到的 D 帳戶**（2026-09-24）：`run.ts SKIP_ACCOUNTS` 列的帳戶不抓（現有 3 個 D 帳戶 1319／1732／24492＝**已移到 MediaGo、停用多年的舊帳戶**，使用者決定略過）。成因：D 平台 API 對 MediaGo 帳戶回 403 `Please use Mediago's API to request.`，而且**從 Cloud Run 連認證都回 `invalid api token`、從公司 IP 認證卻成功**（原因未明，不影響結論）。通則：D 帳戶認證失敗／MediaGo 403 時，**倉庫從未有它的數字 ⇒ `NexusNoRetryError`、訊息帶 `[無法取得]`、不重試、健檢黃燈一行**；以前有數字 ⇒ 一般失敗（重試＋紅燈）。新出現的黃燈帳戶確認是停用帳戶後，加進 `SKIP_ACCOUNTS` 即可。
- **只抓台灣 campaign**：沿用各工具 `getCampaigns` 的 `country_id=tw`。2026-09-24 實測 token 表裡 `HK_Kaiyuan_FAT03`（香港 7 支）、`D2_plarium`（日本 10 支）有非台灣 campaign，但都停在 2023~2024 年初。
- **P 無 advertiser 的事件**：查全平台時會回 advertiser 為空字串的列（事件沒帶 adid；Report Hub 指定 advertiser 查所以從沒遇過）→ 歸到虛擬帳戶 `account_id='(unattributed)'`，不丟（2026-09-21~22 實測只有 12 曝光、0 花費）。
- **抓取**（`fetch.ts`）：D／M 一帳一 job（token 表全部帳戶，M 排除 98 開頭壞資料）；R 用 **Super token + userIds:[]** 一次全平台（2026-09-23 實測 Super 看得到全部代理商）；P 用 `fetchPrismReportAll`（**省略** advertiser_ids＝全部；送空陣列會 500）。D 沿用週報的 campaign 三規則剪枝＋只對 bulk 有資料的 campaign 打 adLists／per-ad／裝置。
- **寫入**（`run.ts writeSlice`）：load job 進暫存表（`nexus__stg_*`，2 小時自動過期）→ 單一 transaction `DELETE 區間(+帳戶) ; INSERT SELECT`。load job 不計費、無 streaming buffer；取代單位＝平台×帳戶×日期區間（R/P 整平台）。
- **防呆**：①列的日期超出 job 區間或帳戶不符 → 拒寫 ②**倉庫原本有數字、這次抓回 0 列 → 拒絕清空、job 失敗重試**（API 抽風不能洗掉歷史）③R 單日超過 10000 列被截斷 → 整個 job 失敗 ④BQ 成功後才寫覆蓋紀錄。
- **Cloud SQL（ad_tools 庫）**：`nexus_jobs`（佇列；失敗 10 分鐘後重試、最多 3 次；心跳停 15 分鐘收回）、`nexus_coverage`（每平台帳戶每天寫了幾列：全空帳戶跳過 BQ、上面的防呆②、狀態頁）。
- **排程**：`/tools/nexus/cron` 每日入列 T-2~T-1（使用者定：抓兩天，T-2 順帶修好 M 洛杉磯時區帳戶的半天數字）；`/worker/cron` 每分鐘，**4 分鐘預算內連續認領**（Cloud Run timeout 600s，D 單帳 2 天實測 125 秒）；全域 GET_LOCK 並發 1。每日優先於回補。
- **回補**：`/backfill/cron?key=&sd=&ed=&platforms=DRMP`，預設 **2026-05-21**（P 最早資料日，使用者拍板）~ T-3。D 14 天一段、R/M/P 30 天一段。
- **排程時間＝台北 04:00**（使用者 2026-09-23 拍板）。~~D token 互踢~~：原本擔心 `getAccessToken` 會讓同 token 舊的 access_token 失效、跟 Report Hub（05:00~06:10）互踢 401；**2026-09-24 實測不會**（同帳號連換三個 access_token 都能打報表，見 discovery-api skill），只抓報表不必錯開排程。R／M／P 的 token 本來就是固定字串、沒有換發流程，也不會互踢。健檢「04:50 後才跑完」黃燈的理由因此變弱，之後可考慮拿掉。
- **成本**：load job 免費；每個有資料的 job 約 4 句 DML（每句最低計 10MB）；P 每 job 呼叫 2 次＝P 後端查 `prism_events` 2 次（dry-run 上限：每日 2 天約 4.76GB/次、回補全段約 113GB 一次性）。
- **每日健檢**（`health.ts`，2026-09-23）：Cloud Scheduler `nexus-health` 台北 **07:00** POST `/tools/nexus/health/cron`（`&dry=1` 只算不發）→ Google Chat（webhook 在 Secret Manager `ad-tools-nexus-chat-webhook` → env `NEXUS_CHAT_WEBHOOK`；**網址即憑證，不可進 repo**）。**每天都發**（正常一行綠燈），因為只在異常才發的話，健檢自己壞掉跟一切正常看起來一樣。只讀 Cloud SQL（比對結果也在 Cloud SQL；只有「批次跑完卻還沒比對」時會先補跑一次比對查 BQ）。檢查：①今天每日批次有沒有入列、跑完沒、幾點跑完（>04:50 黃燈）②近 24h 重試 3 次仍失敗的 job（紅）③各平台 T-1 有沒有資料（紅）、曝光／花費對前 7 天中位數 <50% 紅、>3 倍黃 ④前 3 天天天有花費、T-1 突然沒有的帳戶（黃）⑤正確性比對吻合率（<99.5% 黃、<98% 紅；批次跑完卻沒比對黃）⑥回補進度。門檻在 `HEALTH` 常數。狀態頁最上方即時顯示同一份結果。**偵測不到的**：D/M 新開帳戶沒登錄 token（API 拿不到代理商底下的帳戶清單）。
- **M 裝置表改由 MGID Redash 產生**（2026-09-24，使用者同意；Redash 細節見 memory mgid-redash-source、`core/mgidRedash.ts`）：MGID API 的裝置報表會整支排除「生涯零點擊」campaign，而且只拿得到 token 表裡的帳戶。改成每個批次最後一個 job＝`M` 帳戶 `'*'`（`M_DEVICE_JOB`，「M 裝置（Redash 全平台）」）：
  - 前置：同批次 M 各帳戶 job 還沒跑完就 `NexusDeferError` 延後 5 分鐘（不耗重試次數），因為花費分配要用它們剛寫好的計費金額。
  - 帳戶對照：Redash 的 Client ID（97/98 開頭）≠ token 表 api_client_id（86 開頭），API 也拿不到 Client ID（`/clients/{id}` 只回 id／timezone／wallet）⇒ 用各帳戶 campaign 清單（campaign ID 兩邊同一套）對回。對不上＝token 表缺帳戶 → `account_id='client:<Client ID>'` 照寫不丟、健檢紅燈點名。
  - 時區：每個時區查一次 Redash，帳戶只取自己時區那份（事實表是帳戶本地日）。
  - 花費：Redash 台幣＝美金 × 當天固定匯率（9/23 全帳戶 31.837），跟 API 實際計費差 0.2~0.5% ⇒ `spend`＝該帳戶當天 API 計費（`nexus_coverage`）按 Redash 美金比例分配（尾差補到最大列，加總＝計費）；`spend_usd` 原封存 Redash 美金（含 data fee）。API 沒金額才退回 Redash 換算值。
  - 粒度到 campaign（以前 API 版只有帳戶層），裝置 desktop→PC／mobile→Mobile／tablet→Tablet／其他→Others；轉換只有 conv_buy（查詢只選了 main goal）。
  - M 各帳戶 job 改成 `tables='facts'` 只寫事實表、裝置 job `tables='device'` 只寫裝置表（`buildReplaceSql` 分開刪寫，兩邊不互刪）；裝置 job 不動覆蓋紀錄。回補切 7 天一段。
  - 9/23 全部 46 帳戶都對得上 campaign，含當天補 token 的 868596／872712。
- **M 事實表以 teaser-stat 為準**（2026-09-24，`fetchMAccount`＋`mergeTeaserStat`）：MGID 有兩套數字——statistics-reports（core `fetchMgidReport`）每支有量的 teaser 少幾次曝光（0.05~0.13%），而且**整支不回傳生涯零點擊 teaser**（所屬 campaign 有點擊時，campaign 級零點擊補救也沒涵蓋）；teaser-stat／campaigns-stat／Redash 三者一致且**＝MGID 後台**（AM 確認固力伸 9/23 後台 16,686＝campaigns-stat，statistics-reports 16,674）。做法：statistics-reports 照抓（取 ad_requests 與 teaser 資訊）→ 對「原始列出現過的 teaser＋有數字 campaign 底下全部 teaser」逐支打 teaser-stat → 曝光／點擊／花費／三段轉換蓋掉，teaser-stat 有量但原始列沒有的日子補列。**只改 nexus，core `fetchMgidReport`（Report Hub／週報共用）沒動**。成本：9/23 單日 25 個有數字帳戶序列跑 482 秒（逐支 teaser、150ms 節流）。驗證：9/23 事實 vs Redash 逐帳戶曝光／點擊 **100% 一致**（1,589,340／3,267）。
- **正確性比對**（`recon.ts`，2026-09-24 使用者要求）：每個平台一個「吻合 xx%」，點開看落差帳戶。比的是同一天同一帳戶「事實表（素材層）加總 vs 裝置表加總」的曝光／點擊／花費——兩邊是**同一個 job、同一時間、平台不同的報表查法**（D ad 層 bulk vs campaign 層 platform_cv；R/P/M 不同維度），所以不會因平台事後微調數字而假警報，也**不多打任何平台 API**。**抓不到兩邊共用的前置篩選**：D 剪枝（`pruneDCampaigns` 規則③ updated_at 早於起日 30 天就剪，前提是「投放中系統會更新 updated_at」，這前提若對某支長跑 campaign 不成立，它的花費會兩邊一起消失）、token 表沒登錄的帳戶——使用者 2026-09-24 同意 D 走這個做法。吻合率＝1 − Σ|差| / Σmax（逐帳戶取絕對差，不互相抵銷），取三指標最差；門檻 `RECON`（≥99.5% 綠、≥98% 黃，**待實際跑幾天再調**）。觸發：worker 發現今天每日批次全跑完、且比對時間早於最後一個 job 完成時間 ⇒ 跑一次（重試成功會自動重比）；健檢前再補一次；手動 `/recon/cron?key=&dt=&dry=1`（dry＝只回 BQ 預估掃描量）。結果存 Cloud SQL `nexus_recon`（platform='*' 列是「比對過了」標記），狀態頁與健檢讀這張、開頁面不查 BQ。成本：dry-run 2026-09-23 掃 0.09MB（計費最低 10MB ≈ US$0.00006／次）。
