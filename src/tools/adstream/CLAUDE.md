## AdStream / 廣告凝視者核心（tool#3）
- 目的：把多個 **D + R(Rixbee) + MGID + Prism** 帳戶的原始報表定期寫入使用者指定 Google Sheet：D→`d_bulk_raw_data`、R→`r_bulk_raw_data`、M→`m_bulk_raw_data`、P→`p_bulk_raw_data`；四平台可混搭，另寫 `integrated`／`device_summary`。
- 程式：設定/狀態 `core/store.ts`（表 `adstream_configs`，平台帳號欄 `account_ids`／`r_user_ids`／`mgid_client_ids`／`p_advertiser_ids`，各自游標 `last_synced_d/r/m/p`）；同步核心 `tools/adstream/run.ts`；路由/UI `tools/adstream/route.ts`（route base `/tools/adstream`）。舊 `account_names`／`last_synced_date` 保留作 rollback。
- D 抓取欄位：base 13 欄走 bulk `date, imp, click, ctr, cpc, cpm, charge, cv, cvr, mcv, campaign_id, campaign_name, ad_id`；**per-ad 轉換 12 欄**＝`mcv2`（第二次轉換 base，D 三個 base 轉換 cv/mcv/mcv2 之一，bulk 只回 cv/mcv、mcv2 唯有 per-ad 才有；2026-07-13 補齊對齊週報）＋ **cv_* 細分 11 欄**（`cv_view_content, cv_add_to_cart, cv_app_install, cv_complete_registration, cv_add_paymentInfo, cv_start_checkout, cv_search, cv_add_to_wishlist, cv_purchase, cv_lead, cv_other`）＋ **`ad_name`**（廣告名稱，bulk 只有 ad_id）bulk 無、另打 **per-ad date_reporting** 取得。另 **`headline`（廣告文案標題＝素材 title）** bulk/per-ad 報表端點都沒有，唯有 **`getAdLists`（廣告本身設定 `/ad/{cid}/lists`）** 才有，另打建 ad_id→title 對照接回（`run.ts fetchHeadlineMap`，走併發無 1 req/s 限流；驗證 `poc/verify_d_headline_merge.mts` 命中 50/50）。寫 sheet 前再補 `account_name, synced_at` → **共 29 欄**（順序：account_name, synced_at, base13, ad_name, headline, mcv2, cv11）。per-ad 實測共 36 欄（`poc/verify_d_api_doc.mts`），未採的欄多為裝置細分 `pc_*/mobile_*`（只有 base、無裝置×事件、無 tablet，BI 可自算故不存）
- **cv_* 取法（`run.ts fetchCvDetailMap`）**：bulk 列本身就是「有資料的 ad」，直接拿來當索引（不必另跑 getAdReportIndex 預掃），對去重後的 (campaign_id, ad_id) 打 `getDateReports`(per-ad，**1 req/s 最嚴限流→D 端變慢主因**)，回應以 `date+campaign_id+ad_id`（date 去 -//正規化）接回每一列；找不到補 0。base 用 bulk、cv_* 用 per-ad 拼接安全：bulk base 與 per-ad base 已 poc 對數逐欄相等。per-ad 失敗（getDateReports 內已退避重試）往外拋，由 runConfig 原子性接住（整次不寫、不推進游標）
- **⚠️⚠️ per-ad `date_reporting` 端點單次區間上限「31 天(inclusive)」**：實測 31 天可、**32 天起靜默回 0 列（`data` 空、不報錯，跟 bulk 的 80008 完全不同——超兇的坑，毫無錯誤訊息）**。`fetchCvDetailMap` 原本沒切段、把整段回補區間（可達數月）一次丟 per-ad → cvMap 全空 → **cv_*/ad_name 整片空白**（headline 走 getAdLists 與日期無關、base 走 bulk 已切 7 天，故都正常，只有這條 per-ad 中招＝「API 抓得到卻沒寫入」的真凶）。2026-06-25 修：`fetchCvDetailMap` 比照 `getAdReportBulk` 用 `perAdWindows` 切 ≤30 天一段（留 1 天邊際）依序抓取再合併。**教訓：popin 報表端點各有不同的區間上限（bulk=7 天報錯、per-ad=31 天靜默空），凡傳長區間的呼叫都要先確認該端點上限並切段**。驗證 `poc/verify_peradd_chunk.mts`
- R 抓取（`core/rixbee.ts fetchReport`，dimensions=day/country/group_id/cr_id/cpg_id/ad_channel/ad_target、metrics 空＝回全部含 behavior0-6）：實測 35 欄，**去掉每列重複的分頁 metadata `total_count`** → 34 欄；寫 sheet 前補 `synced_at`（共 35 欄）。R 帳號類型(台客/4A/Super)自動偵測（`run.ts detectRUserType`，搬自週報；混型用 Super），表單只填 Account ID。R token 走全域 env `RIXBEE_*`（非 d_tokens）
- **Prism(P 平台) 抓取（2026-09-14 新增）**：第四來源，設定存 `p_advertiser_ids` JSON，後端以 Secret Manager `PRISM_API_TOKEN` 呼叫 `core/prism.ts`。寫 `p_bulk_raw_data`（素材粒度；不混入會改變 grain 的 domain/slot），保留 11 個原生 metrics；另抓 date×device 寫 `device_summary`。`integrated` 對映 advertiser/campaign/adgroup/creative，無素材圖與 ad link；P 尚無 conversion 事件，cv1~cv4 固定 0。API 前後皆驗欄位，日期解析失敗整個 P 單元失敗且不推游標。驗證 `tests/verify_adstream_prism.mts`。
- **MGID(M 平台) 抓取（2026-07-10 新增，`core/mgid.ts`）**：第三來源，寫新分頁 **`m_bulk_raw_data`**（24 欄：account_name/synced_at + day×campaign×teaser 的 base + 三階轉換）。走 Broadciel 白牌廣告主 API（詳見 skill `mgid-api`：host `api.native.broadciel.com/v1`、Bearer token、URL 用 `Client API ID` 86xxxx）。token 一帳一列在 `nexus.mgid_tokens`（唯一鍵 `api_client_id`，2026-08-24 實測 28 列；其中 `988787` 是誤存 Client ID 的壞資料、API 一律 401/403），`store.ts getMgidTokenById`/`listMgidAccounts`；設定新增欄 `adstream_configs.mgid_client_ids`(JSON)，UI 顯示 client_name、值存 api_client_id。**轉換是固定三階漏斗 `conversionsInterest/Decision/Buy`（非 D/R 的語意事件）** → 事件池 `M_EVENT_POOL=[conv_interest,conv_decision,conv_buy]` 三 chip，`BucketEvent.src` 加 `'M'`、`sumBucketM` 加總次數欄；桶/integrated/device 與 D/R 同構（M teaser 層對映 ad 層、無 group 留空，deviceType desktop/mobile/tablet/smarttv→PC/Mobile/Tablet/Others）。**⚠️ 三個實測坑**：①`statistics-reports` 金額欄 `{amount,currency}` 要攤平、`ctr` 小數、日期區間上限 90 天(已切段)；②**day 維度是「帳戶本地日」→ dateFrom/dateTo 的偏移必須用該帳戶自己的時區**（用 UTC `Z` 會滲入相鄰日、讓「重抓昨天」寫入隔天列）。**2026-08-24 修：不再寫死 `+08:00`**——實測 28 個帳號裡 25 個 `Asia/Taipei`、**2 個 `America/Los_Angeles`（859152／859153，後者光 90 天就有 22,669 列不是空帳）**，寫死台北對這兩帳會切在人家的日中間（實測 859153 單查 `zonedIso`／`tzOffsetMinutes`（兩段逼近，夏令時間切換日也對），`fetchStatWindow` 收 `tz` 參數；台北帳行為完全不變。驗證 `poc/verify_mgid_timezone.mts`（23 項離線＋`REAL=1` 真 API 2 項；已做 2 個變異測試：寫死 +08:00 抓到 12 項、少一次逼近抓到 1
